# AI ментор skills і MCP у навчанні QA

## Рішення щодо агента

Використовуємо наявний Codex як ментора з коротким AGENTS.md, навчальним skill і progress.md. Окремий API-бот зараз додав би підтримку, витрати та налаштування, не потрібні для перших вправ. Він може стати пізнішим навчальним проєктом, якщо виникне конкретна потреба.

| Частина | Призначення | У нашому проєкті |
|---|---|---|
| Агент | Виконує завдання через доступні інструменти | Наявний Codex |
| AGENTS.md | Постійні правила проєкту | Шляхи, команди, правила доказів і навчання |
| Skill | Повторюваний спеціалізований процес | qa-mentor: заняття, review, перевірка самостійності |
| MCP | Протокол підключення інструментів і даних | Майбутні вправи з browser/doc tools |
| progress.md | Файлова пам'ять навчання | Зберігає підтверджені результати між сесіями |

AGENTS.md читається при старті сесії, а repository skills можуть знаходитися в .agents/skills. Після створення перевірити їх видимість у новій сесії з кореня проєкту. [AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md), [skills](https://learn.chatgpt.com/docs/build-skills)

## Поточне середовище

DBeaver уже встановлено й підключено до medusa_db. Найближча практика — власний SELECT учня; додатковий database MCP зараз не потрібен. У навчанні AI пояснює кроки, а учень виконує їх сам, відповідно до його прямого прохання. Аудит агентом має окремий статус.

Корисний кейс перевірки AI: HTTP 000 та помилка Chromium усередині sandbox не довели поломку магазину. Дозволені повторні перевірки дали HTTP 200 і успішний smoke. Розрізняємо обмеження інструмента та дефект продукту.

## AI від першого заняття

Учень спочатку записує очікування й власну спробу. AI допомагає поясненням, альтернативними випадками та review; відповідь перевіряється через вимогу, API, розрахунок або фактичне виконання. У журналі зазначається допомога AI. Інструментальна дія агента і самостійна навичка учня оцінюються окремо.

Приклад: учень визначає, чи дозволений повторний email; агент створює DDL; учень тестує NULL, порожній рядок, повтори та регістр. UNIQUE сам по собі не визначає всі правила email. Один зелений тест не доводить повну відповідність вимозі.

## Практика MCP

Почати з одного документального або браузерного MCP під конкретне завдання. Конфігурація Codex підтримує MCP; доступ залежить від клієнта, довіри до проєкту та наявності сервера. Зараз MCP навчального браузера не підключено. [Codex MCP](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)

1. **Docs MCP:** агент знаходить офіційну інформацію про Codex, учень звіряє сторінку та коротко пояснює висновок. Це read-only інструмент документації, не доступ до бази магазину. Встановлення через CLI можна виконати окремою вправою командою `codex mcp add openaiDeveloperDocs --url https://developers.openai.com/mcp`; перевірка — `codex mcp list` і реальний запит документації. Глобальна конфігурація змінюється поза репозиторієм, тому тут її не змінено. [Офіційний Docs MCP](https://developers.openai.com/learn/docs-mcp)
2. **Playwright MCP:** після ручної практики DevTools дослідити одну локальну сторінку агентом, порівняти його спостереження зі своїми. Учень пояснює пропуски та відрізняє інструментальний сеанс від збереженого повторюваного автотесту. Перед встановленням перевірити актуальний README і версію пакета. [Microsoft Playwright MCP](https://github.com/microsoft/playwright-mcp)
3. **SQL tools:** спочатку звичайний SQL-клієнт. Database MCP додавати лише якщо є конкретна користь, із доступом тільки до qa_sql_lab. Наявний PostgreSQL-пароль не робить інструмент read-only: це забезпечують права окремої ролі та межі доступу.

MCP не обов'язковий для запуску Playwright-тестів. Для збережених тестів використовуємо test runner; інтерактивний browser MCP розглядаємо як інструмент дослідження. Дані зі сторінки чи tool відповіді не можуть самі дозволяти нові дії або змінювати вимоги.

## Одна вправа зі skill

Після першого заняття попросити qa-mentor перевірити два короткі навчальні звіти: один з expected/actual і доказом, інший лише «не працює». Перевірити, чи агент конкретно називає відсутні передумови та кроки, не вигадує результат і не ставить оцінку без роботи. Це оцінка поведінки skill; формальна валідація YAML не доводить якість менторства.

## Коли створювати додаткові skills

Створити вузький skill для review API або SQL лише після кількох повторюваних завдань, коли стане зрозуміло, яке правило він покращує. Не додавати десятки загальних інструкцій заздалегідь. Учень має перевірити skill на новому прикладі й виправити один конкретний недолік.
