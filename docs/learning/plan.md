# Персональна програма Test Automation: TypeScript + Playwright

## Поточний маршрут від 18 листопада 2026

Ціль — General QA з автоматизацією або Junior QA Automation. Практична база — Medusa, темп — 1–2 години на тиждень. Цей маршрут уточнює порядок найближчих занять нижче. Поточний результат і докази ведемо в [progress.md](progress.md).

1. **CI, 2–3 заняття.** Перевірити створення ключа вітрини та його прив’язку до каналу продажів у seed. Передати ключ із тестової CI-бази в середовище storefront. Отримати перший успішний запуск GitHub Actions і знайти завантажений звіт. Якщо запуск впаде, знайти перший невдалий крок і пояснити причину за логом.
2. **Самостійний UI-тест, 2 заняття.** Для `/dk/products/sweatshirt` зафіксувати передумови та перевірити поведінку кнопки кошика до й після вибору доступного розміру. Пояснити локатор, `await` та очікування Playwright. Додати fixture лише коли з’явиться повторювана підготовка.
3. **HTTP, API та SQL, 2–3 заняття.** Дослідити запит каталогу в DevTools. Написати API-тест зі статусом і перевіркою конкретних даних. У DBeaver виконати власний SELECT для того самого товару в режимі читання. Пояснити, які дані може показати API та що окремо підтверджує БД.
4. **Проба backend і портфоліо, 2–3 заняття.** Зробити малий локальний endpoint на TypeScript для приймання результату тесту, з валідацією та позитивною і негативною перевірками. Підготувати README з командами запуску, посиланням на CI та одним прикладом розбору падіння. Після вправи вирішити, чи поглиблювати QA Automation, чи вивчати backend системно. Python додати за конкретною ціллю.

Кожне заняття має одну зміну та її доказ. Ти робиш першу спробу і запускаєш перевірку. Ментор дає підказку та review, а рівень допомоги фіксуємо в журналі. Раз на чотири заняття — коротка самостійна задача на новому випадку.

Оновлено: 15 жовтня 2026. Формат — навчальний проєкт із практикою розробки тестів, code review та CI/CD.

## Мета та вихідна точка

Мета — самостійно розробляти, пояснювати та підтримувати автоматизацію Medusa-магазину: тест-дизайн, TypeScript, UI/API, дані, Git, CI та розгортання на тестове середовище. Результат — відтворюваний репозиторій з обґрунтованим покриттям, а не задана кількість тестів або обіцянка роботи.

Учень має майже два роки manual Desktop QA, повідомив про нерегулярний SQL; web/API ще потребують практичної перевірки. Учень запустив готовий Playwright-тест (наданий лог: 1 passed), пояснив дві перевірки й межі їхнього покриття. Клас CatalogPage розбирали з підказками; типи, посилання, конструктор і async/await ще не засвоєні самостійно. Самостійне написання POM, fixtures та CI не підтверджене.

Публічні навчальні програми EPAM — орієнтир для основ програмування, Git, тестування та оцінювання. Цей план — наша адаптація під Playwright і магазин; він не відтворює внутрішній стандарт EPAM. Публічний roadmap EPAM прямо зазначає, що програми різняться між курсами й локаціями.

## Домовленість про навчання

- Код навчальних вправ пише учень. Ментор пояснює, дає обмежений приклад і перевіряє спробу. Прохання створити структуру означає папки та порожні файли, якщо реалізація окремо не замовлена.
- Пряме прохання реалізувати конкретну частину дозволяє це зробити; результат AI позначаємо окремо від навички учня.
- Пояснюємо технічно точно: синтаксис, типи, час виконання, область видимості, життєвий цикл і причину рішення. Терміни українською з англійським відповідником. На прохання додаємо навчальні коментарі.
- Один крок містить конкретну зміну, її призначення, спосіб перевірки та очікуваний результат. Після пояснення — практика, а не довга серія питань на пригадування. Якщо відповідь помилкова, змінюємо приклад і даємо малу дію для перевірки розуміння.
- На початку заняття називаємо місце поточного кроку в загальній архітектурі. Показуємо цільову картину, а реалізуємо поступово.
- Сеанс 30–60 хвилин; короткий варіант — 15 хвилин. Бюджет 1–2 години на тиждень. Після чотирьох сеансів оцінюємо темп; строки залежать від практики та діагностики.
- Не повторюємо встановлення працюючих інструментів. Діагностика середовища — до 15 хвилин, потім явно позначений підготовлений приклад.

## Робочий цикл кожної функції

1. Визначити ризик, вимогу й незалежне джерело очікуваного результату.
2. Дослідити поведінку вручну та вибрати рівень перевірки: unit, API/integration або UI E2E.
3. Записати сценарій із передумовами, даними та очікуванням.
4. Учень реалізує невелику зміну; ментор проводить code review.
5. Перевірити локальний запуск і контрольований негативний випадок. На тестових даних навмисно порушити одне очікування та пояснити повідомлення про помилку.
6. Переглянути diff, зробити commit/PR і перевірити результат Actions, коли Git та CI доступні.
7. Зберегти доказ, рівень допомоги й наступну дію у progress.md.

## Маршрут і критерії переходу

| Етап | Що вивчаємо | Артефакт і критерій |
|---|---|---|
| 1. TypeScript через CatalogPage | Значення й тип; параметр і аргумент; import/export; class, instance, this, constructor, readonly; посилання; метод; Promise, async/await | Учень підключає CatalogPage до тесту, пояснює передачу Page, сам змінює один параметр і виправляє помилку типу |
| 2. Структура UI-тесту | describe/test; setup/action/assert; Locator; getByRole/getByTestId; точні локатори, auto-wait та повторні assertions | Каталог і вибір варіанта; учень розрізняє видимість, доступність кнопки та успішність дії |
| 3. POM і components | Локатори й дії в класах; assertions сценарію у spec; композиція; ProductPage, CartPage, Header | Учень переносить локатори в класи й реалізує нову дію без копіювання готового рішення |
| 4. Fixtures і життєвий цикл | Типізований extend; use; test scope; setup/teardown; beforeEach; test.step; теги smoke/regression | Об’єкти створюються через fixtures для кожного тесту; два сценарії проходять окремо й разом |
| 5. Перший CI | Git diff/branch/commit/PR; команди npm; окремий tsc і lint; env; чиста БД; bootstrap; health; Chromium; report/trace/logs | Один зрозумілий smoke проходитиме на чистому runner; учень пояснює одну навмисну помилку CI |
| 6. API та дані | HTTP, headers, JSON, auth, статус і зміст; APIRequestContext; типізований клієнт; фабрики; cleanup; SQL SELECT/JOIN | Створення окремого кошика через API, позитивний і негативний тест; секрети не потрапляють у Git або звіт |
| 7. Кошик і checkout | Кількість, суми, видалення; валідація адреси; доставка; тестовий платіж; підтвердження order | Ізольовані дані, незалежний розрахунок суми; один UI E2E і детальні правила через API там, де це доречно |
| 8. Акаунт і регресія | Унікальні користувачі; auth/storageState; власні замовлення; регіони; 404; API-помилки; data-driven cases | Немає залежності від порядку тестів або загального кошика; перевірена ізоляція доступу двох тестових користувачів |
| 9. Надійність і масштаб | Trace/debug; flaky analysis; retries; паралельність після ізоляції; браузери й мобільний профіль; нічний запуск; unit для власної чистої логіки | Учень відрізняє дефект продукту, тесту та середовища; пояснює причину нестабільного тесту й виправлення |
| 10. CD та завершення | Staging; незмінний build artifact; secrets/environments; deploy; smoke після deploy; rollback; міграції; портфоліо | На вибраному хостингу розгортається перевірена збірка, невдалий smoke зупиняє просування; описано відкат застосунку та межі відкату БД |

Це послідовність залежностей, а не десять занять. TypeScript, HTTP, Git та тест-дизайн продовжуємо в кожному етапі. Git починаємо одразу після підтвердження доступності, не відкладаючи до CI. Не чекаємо завершення всього UI-покриття для першого Actions.

| P1 | Акаунт | Реєстрація, вхід/вихід, негативна авторизація, адреси, власні замовлення |

## Правила архітектури

- Класи Page Object і компонентів — обраний навчальний підхід. Спільну поведінку виділяємо через композицію. BasePage/успадкування додаємо лише за конкретної потреби.
- Spec описує поведінку й очікуваний результат; Page Object приховує локатори та механіку взаємодії. API-клієнт відповідає за HTTP; фабрика — за створення даних.
- describe групує за функцією; beforeEach додаємо для реальної спільної передумови; fixtures керують залежностями й очищенням; test.step виділяє змістовні етапи сценарію.
- Використовуємо надійні локатори й web-first assertions. Не покладаємося на waitForTimeout або випадкові CSS-класи. Тест повинен падати при порушенні перевірюваного правила.
- Окремий browser context не ізолює БД. Кошики, користувачі й mutable data належать тесту; worker scope використовуємо лише після розбору його наслідків.
- Очікувану ціну/суму беремо з погоджених даних і незалежного розрахунку, не копіюємо з того ж UI, який перевіряємо. Порівняння API та UI перевіряє узгодженість, але саме по собі не доводить правильність ціни.
- На старті достатньо HTML report і trace Playwright. Додаткові репортери, шардінг та абстракції додаємо для конкретної задачі.

## CI/CD і готовність середовища

Поточний workflow є, але його успішність на GitHub не підтверджена. Перед розширенням перевіряємо сумісну версію Node/npm, lockfile, test scripts, TypeScript/lint, test env, міграції й seed на чистій одноразовій БД, sales channel/publishable key, залишки та готовність HTTP endpoints. Playwright трансформує TypeScript, але не замінює tsc.

PR: статичні перевірки та короткий smoke. Main: ширший UI/API набір. Schedule: розширена регресія та вибрані браузери. Це цільова схема, а не вже налаштована конфігурація. Звіти й діагностика зберігаються також при падіннях. Retry не вважаємо виправленням flaky-тесту; падіння з успіхом на повторі потребує розбору. Час і стабільність вимірюємо після появи запусків, без вигаданих KPI.

CD починається після вибору staging-хостингу фронтенда, бекенда й БД. Випускаємо перевірений artifact; після розгортання — health і smoke. Правила production deployment та доступність захисту GitHub Environments залежать від репозиторію й тарифу. План відкату коду не означає автоматичну оборотність міграцій БД.

У навчальному режимі сервіси запускає учень. Не скидаємо локальні дані заради CI. DDL/DML-вправи — лише в окремій qa_sql_lab; її ще треба створити. Живий checkout, admin login і CI залишаються непідтвердженими до фактичних перевірок.

## Найближчі чотири сеанси

1. CatalogPage: розібрати типи й constructor, підключити через new у тесті; describe, запуск, контрольована помилка. Артефакт — власний refactor і пояснення учня.
2. Locator і assertions: перенести локатори каталогу в клас; учень додає перевірку товару через ProductPage. Артефакт — сценарій і code review.
3. Типізована fixture, test isolation, теги; самостійний сценарій вибору M. Артефакт — незалежний запуск і пояснення життєвого циклу.
4. Чистий запуск Actions: один smoke, test env, одноразова БД, report/trace. Якщо bootstrap потребує більше часу, виділити окрему технічну сесію; учень має пояснити кожен доданий крок. На новому товарі перевірити перенос навички й переглянути темп.

SQL SELECT із lesson-01 не виконаний і залишається в backlog; він не блокує поточну практику TypeScript. Web/Network пояснюємо на досліджуваних переходах; прямий запит до Medusa не зобов’язаний з’являтися в браузері через серверні data-функції Next.js.

## Оцінювання та докази

Окремо оцінюємо правильність, обґрунтування й самостійність за шкалою 0–3: 0 — доказу немає; 1 — істотні помилки або готове рішення; 2 — правильний результат із невеликою підказкою; 3 — самостійне виконання й перенесення на новий випадок. Відсутність перевірки позначаємо явно; код AI не зараховуємо як навичку учня.

Перехід: правильність і обґрунтування не нижче 2 та новий випадок із самостійністю не нижче 2. У review перевіряємо коректність сценарію, джерело очікування, локатори, очікування асинхронних дій, ізоляцію, типи та якість повідомлення про падіння.

Готовність навчальної зміни: учень пояснює код; перевірка пройшла; контрольований негативний випадок дав очікуване падіння; diff переглянуто; CI перевірено після його налаштування; доказ і допомогу записано. Мікрокрок не потребує всього циклу окремо — ці умови застосовуємо до завершеного сценарію.

Докази — код у tests/, результати запусків і короткі роботи в docs/learning/submissions/. Англійські назви тестів/PR поступово вводимо з поясненням. AI використовуємо для пояснення, review і діагностики з незалежною перевіркою. Через кожні чотири сеанси — самостійний новий випадок і перегляд програми.
