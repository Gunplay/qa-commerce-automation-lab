# Ідеї Claude Code для навчання QA з Codex

Підготовлено 21 жовтня 2026. Читання: орієнтовно 25–35 хвилин, можна двома частинами.

Твоя мета — навчитися ставити AI перевірювані завдання, розбирати його пропозиції та автоматизувати повторювану роботу з тестами магазину. Почнемо із запитів, правил проєкту та skills. Браузерні інтеграції й автоматичні дії додамо під конкретну потребу.

Джерело ідей — авторський [Claude Code Everything You Need to Know](https://github.com/wesammustafa/Claude-Code-Everything-You-Need-to-Know). Його приклади належать до Claude Code; нижче наведена наша адаптація до навчального проєкту. Можливості Codex звіряємо з офіційною документацією OpenAI.

## 1 Що варто взяти для себе

| Ідея | Просте пояснення | Користь для тебе | Коли застосовувати |
|---|---|---|---|
| Чіткий prompt | Запит із завданням, контекстом і критерієм результату | Отримувати допомогу потрібного обсягу | У наступній вправі |
| Правила проєкту | Постійні домовленості для агента | Менше повторювати шляхи й формат навчання | У нас уже є AGENTS.md |
| Skill | Інструкція для повторюваного процесу | Однаково перевіряти якість тестів | Спочатку випробувати критерії вручну |
| Workflow | Послідовність роботи | Не пропускати аналіз і перевірку | На REG-04 |
| MCP | Спосіб надати агенту зовнішні інструменти | Досліджувати сторінку за допомогою AI | Після основ тесту й CI |
| Hook | Скрипт, що запускається на певну подію | Автоматизувати рутинну перевірку | Коли зрозуміло, що повторюємо |
| Subagent | Окремий агент для частини роботи | Розділити великий аудит | Пізніше, за потреби |

Автор розглядає ці механізми у [README](https://github.com/wesammustafa/Claude-Code-Everything-You-Need-to-Know#when-to-use-what). Черговість у таблиці підібрана під наше навчання.

## 2 Як переносити ідеї між інструментами

Переносимо зміст інструкцій, а спосіб підключення обираємо для конкретного клієнта.

| У прикладах Claude Code | У нашому проєкті з Codex |
|---|---|
| CLAUDE.md із правилами | Наявний [AGENTS.md](../../AGENTS.md) |
| Повторювані інструкції в .claude/commands або .claude/skills | Локальний skill у .agents/skills із SKILL.md |
| Команда /review | Спочатку звичайний запит на review; після перевірки процесу — наш skill |
| Налаштування MCP для Claude | Окрема конфігурація Codex для обраного MCP |
| Hooks і файли агентів | Потребують перевірки сумісності з нашим клієнтом |

Codex використовує AGENTS.md для правил проєкту та підтримує локальні skills у `.agents/skills`. Skill містить SKILL.md і може мати допоміжні матеріали. MCP має власне налаштування; конфігурацію Claude не варто копіювати як конфігурацію Codex. [Правила проєкту](https://learn.chatgpt.com/docs/agent-configuration/agents-md), [skills](https://learn.chatgpt.com/docs/build-skills), [MCP](https://learn.chatgpt.com/docs/extend/mcp?surface=cli).

У нас уже є розподіл відповідальності: AGENTS.md задає правила, [qa-mentor](../../.agents/skills/qa-mentor/SKILL.md) описує заняття, [progress.md](progress.md) зберігає навчальний контекст, а [Excel](artifacts/site-automation-plan.xlsx) — покриття та результати запусків. Новий матеріал доповнює цю структуру.

## 3 Як формулювати запит до AI

**Контекст** — інформація, потрібна для розуміння задачі: файл, сценарій, помилка, очікуваний результат. **Критерій завершення** — ознака, за якою можна перевірити виконання.

Замість «зроби хороший тест» вкажи:

1. Що перевіряємо.
2. Де шукати наявний код і вимоги.
3. Який обсяг допомоги потрібен.
4. Який результат очікуємо отримати.

Приклад запиту для наступного заняття:

```text
Ми працюємо над REG-04 — обов’язковими полями реєстрації.
Прочитай progress.md та актуальний кейс в Excel.
Переглянь tests/ui/registration.spec.ts і tests/pages/registrationPage.ts.
Поясни, чим новий негативний сценарій відрізняється від успішної реєстрації.
Дай одну невелику зміну для моєї спроби й критерій її перевірки.
Повне рішення поки не пиши.
```

Для review власної роботи:

```text
Перевір мої зміни для REG-04, файли не редагуй.
Оціни сценарій, локатори, assertions та незалежність тесту.
Для кожної проблеми вкажи місце, причину й мінімальне виправлення.
Окремо назви, що встановлено з коду, а що потребує запуску.
```

Це наші шаблони. Вони розвивають запропонований автором підхід до [постановки завдань](https://github.com/wesammustafa/Claude-Code-Everything-You-Need-to-Know#prompt-engineering-deep-dive).

Фраза «тест правильний» потребує пояснення: яке правило він перевіряє, звідки взято очікування і що саме було запущено. Зелений результат показує проходження наявних перевірок; пропущене правило він не перевіряє. Наприклад, видимість форми сама по собі не доводить, що вона забороняє порожній email.

## 4 Як організувати роботу над одним тестом

Автор пропонує послідовність дослідження, планування, реалізації та фіксації змін. Для нашої вправи додамо явну перевірку очікувань і результату.

```text
Вимога → дослідження → короткий план → твоя зміна → review → запуск → доказ
```

| Крок | Що робимо на REG-04 | Що має залишитися |
|---|---|---|
| Вимога | Уточнюємо обов’язкові поля та очікувану поведінку | Сценарій із джерелом очікування |
| Дослідження | Дивимося на форму й наявний RegistrationPage | Розуміння поточної поведінки |
| План | Обираємо один випадок із порожнім обов’язковим полем | Кілька конкретних кроків |
| Зміна | Ти додаєш невелику частину сценарію | Код, який можеш пояснити |
| Review | Перевіряємо сенс сценарію й реалізацію | Обґрунтовані висновки |
| Запуск | Ти запускаєш погоджений тест | Лог або звіт |
| Доказ | Після завершення оновлюємо трекер | Дата, статус і посилання на доказ |

**Diff** — різниця між версіями файлів. Перед збереженням змін переглядаємо diff, щоб бачити весь фактичний обсяг роботи. **Commit** — зафіксований набір змін у Git із поясненням.

## 5 Який skill може бути корисним нам

Пропонована майбутня назва — `qa-playwright-review`. Його задача: перевіряти конкретний UI-тест за узгодженими критеріями. Тут описаний задум; файл skill ще не створений.

Спочатку застосуємо критерії звичайним запитом на двох-трьох власних змінах. Це покаже, які інструкції справді корисні й що уточнити перед оформленням skill.

### Критерії review

| Питання | Що воно допомагає помітити |
|---|---|
| Яке правило перевіряє тест? | Назва ширша за фактичні перевірки |
| Звідки відомий expected result? | AI або поточний UI самі визначили «правильну» поведінку |
| Чи однозначний locator? | Вибирається інший елемент із такою самою назвою |
| Чи assertion перевіряє результат дії? | Клік виконано, але наслідок не перевірено |
| Чи коректні асинхронні очікування? | Пропущений await або довільна затримка |
| Чи тест працює незалежно? | Залежність від покупця чи сесії попереднього тесту |
| Які дані він створює? | Накопичення користувачів або конфлікти спільних даних |
| Який доказ виконання є? | Review коду помилково названо успішним запуском |

**Locator** знаходить елемент сторінки. **Assertion** перевіряє очікуваний результат. **Ізоляція тестів** означає, що результат одного сценарію не залежить від виконання іншого. Надійні локатори, незалежність і assertions із повторними перевірками описані в [Playwright Best Practices](https://playwright.dev/docs/best-practices).

### Місце review у нашій архітектурі

Поточний [registration.spec.ts](../../tests/ui/registration.spec.ts) описує успішну реєстрацію та перевіряє кабінет після reload. [RegistrationPage](../../tests/pages/registrationPage.ts) містить відкриття форми, заповнення та submit.

У нашому підході дії сторінки залишаються в класовому POM — Page Object Model, об’єкті для роботи зі сторінкою. Очікування конкретного сценарію зберігаємо у spec. Майбутній skill перевірятиме цю домовленість разом зі змістом тесту.

### Як перевіримо сам skill

Візьмемо коректний фрагмент і навчальний приклад із відомою помилкою. Skill має пояснити проблему з посиланням на код, зберегти погоджений обсяг і не вигадати результат запуску. Потім застосуємо його до нового випадку. Оформлена інструкція ще не доводить якість review.

## 6 Що потрібно змінити у шаблонах автора

### Шаблон test

Файл автора [test.md](https://github.com/wesammustafa/Claude-Code-Everything-You-Need-to-Know/blob/main/.claude/commands/test.md) орієнтований на **unit tests** — перевірку окремої внутрішньої логіки. Він обмежує реальні HTTP-виклики та вводить вимоги до mocks — замінників зовнішніх залежностей.

Наша реєстрація — **UI E2E**, перевірка шляху користувача через браузер і застосунок. З шаблону корисні увага до граничних випадків і перевірка результату; правила unit-тестів не переносимо на весь UI-набір. Також у ньому є вимога щонайменше чотирьох субагентів. Для одного навчального тесту я не бачу практичної потреби в цьому.

### Шаблон review

Файл [review.md](https://github.com/wesammustafa/Claude-Code-Everything-You-Need-to-Know/blob/main/.claude/commands/review.md) охоплює кілька професійних ролей і вимагає негайного впровадження покращень та оновлення GitHub.

У нас review спочатку дає конкретні висновки щодо замовленої зміни. Подальшу реалізацію визначає поточне завдання. Це дозволяє розібрати причину помилки й не розширити вправу на весь магазин.

## 7 Для чого нам браузерний MCP

**MCP — Model Context Protocol**: протокол, через який агент отримує доступ до інструментів. Браузерний MCP дозволяє відкривати сторінки, досліджувати їхню структуру й виконувати дії. Можливості залежать від підключеного сервера. [Офіційний Playwright MCP](https://github.com/microsoft/playwright-mcp).

| Інструмент | Його роль у нашій роботі |
|---|---|
| Codegen | Записує дії користувача як початковий код |
| Playwright Test | Виконує збережені сценарії та assertions локально й у CI |
| Playwright MCP | Дає AI інструменти для інтерактивного дослідження браузера |

Докладніше про запис дій та перевірок: [Playwright Codegen](https://playwright.dev/docs/codegen-intro).

Майбутня вправа: на `/dk/account` порівняти твої спостереження про форму з висновками агента, знайти пропуски й потім сформулювати тест. Проходження форми агентом не створює автоматично підтримуваний сценарій у нашому репозиторії.

Microsoft також описує варіант **CLI + skills** для роботи coding agents із браузером. Перед підключенням порівняємо його з MCP за конкретною задачею; інсталяція MCP не є обов’язковим етапом навчання. [Порівняння Microsoft](https://github.com/microsoft/playwright-mcp#playwright-mcp-vs-playwright-cli).

## 8 Що залишити на пізніше

**Hooks** корисні для автоматичної реакції на подію, наприклад форматування після редагування. Почнемо зі зрозумілої ручної перевірки типів; автоматизацію підбиратимемо до клієнта й узгодженого процесу. Масовий запуск E2E після кожної дрібної зміни зараз створював би зайвих покупців: поточний тест реєстрації створює нового користувача, cleanup — очищення тестових даних — ще немає.

**Subagents та agent teams** розподіляють роботу між агентами. Потенційний випадок для нас — великий аудит UI, API та CI. Для розбору одного методу RegistrationPage достатньо послідовної роботи.

**Memory MCP** зберігає контекст між сесіями. Навчальну пам’ять уже ведемо у progress.md, а результати автоматизації — в Excel. Окреме сховище варто додавати, коли з’явиться потреба, яку ця схема не покриває. [Огляд інтеграцій автора](https://github.com/wesammustafa/Claude-Code-Everything-You-Need-to-Know/tree/main/mcp-servers).

## 9 Як підготуватися до практики

### Перше читання на 15 хвилин

Прочитай розділи 1–4. Сформулюй своїми словами різницю між запитом, постійним правилом і skill. Підготуй один власний запит на допомогу з REG-04 за прикладом розділу 3. Нічого встановлювати для цього не потрібно.

### Друге читання на 15–20 хвилин

Прочитай розділи 5–8. Подивися на registration.spec.ts і вибери два критерії review, які можеш пояснити на його прикладі. Підготуй коротку відповідь: чому керування браузером через AI та запуск збереженого автотесту дають різні результати роботи?

### Самоперевірка

1. Коли достатньо звичайного запиту, а коли варто оформити skill?
2. Де у нашому проєкті живуть правила й навчальний контекст?
3. Чому видимість форми не доводить валідацію обов’язкових полів?
4. Чому порада «запусти npm test» може бути непридатною до конкретного репозиторію?
5. Який результат review можна підтвердити читанням коду, а який потребує виконання?

Для четвертого питання підказка є в [AGENTS.md](../../AGENTS.md): поточний npm test не підтверджує проходження наших UI-тестів.

Готовність до практики: можеш дати конкретний запит, пояснити вибрані критерії review та назвати доказ виконання тесту. Незрозумілі терміни випиши — розберемо на коді.

## 10 Як застосуємо це в проєкті

Це пропонований порядок практики в межах нашого бюджету 1–2 години на тиждень. Він доповнює поточне REG-04 та наступну роботу з CI.

| Крок | Що робимо разом | Критерій завершення |
|---|---|---|
| 1 | Використовуємо твій чіткий запит під час REG-04 | Ти пояснюєш сценарій і робиш одну зміну |
| 2 | Перевіряємо тест за критеріями розділу 5 | Кожне зауваження має причину й місце в коді |
| 3 | Після повторного використання оформлюємо вузький skill | Він помічає відому помилку та коректно оцінює новий приклад |
| 4 | Продовжуємо CI та зберігаємо докази запусків | Підтверджений результат GitHub Actions або конкретний розібраний блокер |
| 5 | За потреби обираємо браузерний інструмент | Порівняння твоїх спостережень і дій агента на одній сторінці |

Налаштування виконуватимемо під час відповідної практики. Підготовка матеріалу не змінює статусів покриття тестами або оцінки твоїх навичок.

## 11 Що читати в оригіналі

Не обов’язково читати весь англомовний репозиторій підряд. Для підготовки достатньо таких частин:

1. [Prompt Engineering](https://github.com/wesammustafa/Claude-Code-Everything-You-Need-to-Know#prompt-engineering-deep-dive) — зверни увагу на порядок дослідження й реалізації.
2. [Skills](https://github.com/wesammustafa/Claude-Code-Everything-You-Need-to-Know#claude-skills) — розбери ідею повторюваної інструкції.
3. [test.md](https://github.com/wesammustafa/Claude-Code-Everything-You-Need-to-Know/blob/main/.claude/commands/test.md) — знайди, для якого рівня тестування написаний шаблон.
4. [review.md](https://github.com/wesammustafa/Claude-Code-Everything-You-Need-to-Know/blob/main/.claude/commands/review.md) — поміть, де перевірка переходить у зміну коду.

Команди встановлення, моделі й налаштування перевіряй за документацією відповідного продукту перед використанням. Сторонній skill потрібно прочитати: він може містити вказівки редагувати файли, запускати команди чи публікувати результат.

Для продовження скажи: «Прочитав матеріал про Claude Code. Розберімо мій запит для REG-04 і застосуймо критерії review до моєї спроби».
